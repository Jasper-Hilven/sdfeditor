# 30.8 — The level file `computer.level` and its tests

Goal: `content/levels/computer.level` fills every section of 30 with the real models (all exist after 30.3-30.7; room look after 30.2, emission after 30.1) and the tests accept it. Scene name Computer (the file name decides it).

Steps:
1. Write the file in the commenting style of `content/levels/toybox.level`: header with the 250x scale and theme; `play size=(160, 120) noise=0`; `room size=(160, 64, 120) walls=case-wall ceiling=case-glass glow=all ...` with 30's light values; `machines set=computer`; `regions base=pcb` with `trace` (three buses per side, three parallel traces 0.8 m wide 1.6 m apart, 45 degree jogs, mirrored, as in 30 "Regions"; if the region format cannot express this, extend it minimally or use rectangles, and say so), `silk`, `pad` (`wobble=0`); the two `sides` (RAM banks, gate slot, flag stand, spawn, pods, four turrets and a machine zone per side) and the neutral pods per 30; the landmarks (each group starting with a comment line); scatter `parts` main and accent layers, thermal paste hand-placed; trees `smd` and `components` sections; `draw` groups. The pulse flags and the `pulses` line belong to 30.9, not here.
2. Tests: `computer` in `BattleSidesTests.LevelNames` with its weapons (minigun, poison-gun, electro-gun, flamethrower) and `MachineLevels`; `ContentComputer_HasOnlyComputerParts` (like `ContentToyBox_HasOnlyToys`: models from `computer/`, the pickups, weapons, battle objects or the computer machines; no material from another theme); LevelFileTests and the scatter tests pass. When a clearance test fails, change numbers in the file (not the tests), keeping 30's intent, and say so. Every placed model keeps 10 m from pods, stands and spawns.
3. Bake: `dotnet run --project SDFPipeline.Cli -- level content/levels/computer.level --into Unity/Assets/Level/Generated/computer`; report instance counts and sizes.

Check: `dotnet build`, `dotnet test`. Acceptance: the bake succeeds, all tests pass, the layout mirrors across x = 0. Dependencies: 30.1-30.7.

Common rules (every subticket of 30): read `tickets/30-inside-computer-level.md`, `tickets/README.md`, `tickets/done/26-level-ruleset.md` and the 27 subtickets that built the generic pieces (`tickets/done/27.1-room-looks.md`, `27.2-machine-sets.md`, `27.3-path-movers.md`) first. Work only in this worktree (the absolute path the lead gives you), never the main checkout. Meshing at 256 cells, 3 LODs (`sdf mesh <model> --resolution 256 --lods 3`, no `--suffix`), never 512. Each SDF pointer id is one node (reuse only via variables). One theme per scene: computer hardware only, no text anywhere, no cyan, team colours only where 30 allows. Toon look only, no live raymarching, nothing that needs compute shaders (WebGL2). HUD elements about 5 px from the screen edges. 42 is they/them. Other tickets (28 kitchen, 29 bathroom, 33 boss) are being built in parallel on other branches and extend the same shared level code (`SDFPipeline/Levels/*`, `LevelBuilder.cs`, toon and room shaders): add rather than rewrite, keep new features generic and in their own files where you can, and keep edits to shared files small so merges stay easy. Generated files (glbs, mesh assets, level bakes, Unity-generated prefabs and scenes) are not in git; do not commit them. Match surrounding code style and comment density. Do not commit (the lead commits). Do not spawn agents. Where the ticket text says `machines look=computer` the real line is `machines set=computer` (27.2). Open questions of 30 are answered with its defaults: red/blue RAM light bars, the machines keep the scouts' floating eyes, the pulses boost +35% for 2.5 s. Report: files changed, commands run, test results (failures stated honestly), what is left for a human look.
